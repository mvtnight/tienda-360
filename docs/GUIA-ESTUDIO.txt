2. FLUJO (dilo en 3 frases)
--------------------------------------------------------------------------------
1) El usuario abre la SPA y hace login con Azure AD: MSAL v5 usa Authorization
   Code + PKCE (code_verifier + code_challenge S256, state y nonce). No hay
   secretos, es un public client: solo redirectUri + clientId.
2) MSAL canjea el code en el backend de Azure y devuelve un access_token cuyo
   aud es api://6da3f8f4... y scope access_as_user. El interceptor adjunta
   Authorization: Bearer <token> a las llamadas al BFF (local) o al API Manager.
3) El API Manager (API Gateway) valida el JWT en TODAS las rutas: firma JWKS,
   issuer = login.microsoftonline.com/<tenant>/v2.0, audience = api://<client-id>,
   y exige scope access_as_user. Sin token -> 401, token sin scope -> 403.
4) Si es valido, proxya al ALB -> EC2 backend (:8090). El backend RE-valida y
   aplica RBAC: cualquier autenticado lee; ADMIN o VENDEDOR crea; solo ADMIN
   cambia estado o elimina. Mismo JSON circula validado 3 veces (BFF, API GW,
   backend) = defense in depth.

MATRIZ 200/401/403 (aprenderla):
  sin token                 -> 401 (autorizador JWT)
  token invalido            -> 401 (firma JWKS no verifica)
  token valido sin scope    -> 403 (authorizer scopes)
  GET/POST maria o jose     -> 200/201
  PATCH/DELETE maria        -> 403 (RBAC: rol vendedor)
  PATCH/DELETE jose         -> 200 / 204 (RBAC: rol admin)

3. QUE VALIDA CADA CAPA (pregunta casi segura del profe)
--------------------------------------------------------------------------------
- BFF (JwtDecoderConfig): descarga JWKS de discovery/v2.0/keys, firma RS256,
  iss (login.microsoftonline.com/<t>/v2.0 o sts.windows.net/<t>/), aud
  (clientId o app URI), exp/nbf. Falla -> 401.
- API Manager (API Gateway): authorizer JWT con issuer Y audience; por eso es
  "el mismo criterio que el BFF". IdentitySource = header Authorization.
  AuthorizationScopes = access_as_user -> token sin scope = 403.
- Backend: OAuth2 Resource Server + @PreAuthorize. Normaliza claim 'roles'
  (minusculas de Azure) a ROLE_PEDIDOS_* en mayusculas para el RBAC.
  /health es permitAll (lo usa el health-check del ALB).

CLAVE PARA DEFENDER: "¿Por que validar el token 3 veces?" -> porque son 3
superficies de confianza distintas; ningun componente confia en el otro.

--------------------------------------------------------------------------------
4. PREGUNTAS PROBABLES + RESPUESTA CORTA
--------------------------------------------------------------------------------
Q: ¿Por que Authorization Code + PKCE y no Implicit?
R: Implicit expone el token en la URL y no se recomienda; PKCE envía solo un
   code_challenge S256 y canjea el code por el token sin secretos, ideal para
   SPAs (public client). El access_token nunca aparece en la URL.

Q: ¿Que valida state y nonce?
R: state -> anti-CSRF (lo genera la app y Azure lo devuelve igual); nonce ->
   anti-replay en el id_token. MSAL los maneja automáticamente.

Q: ¿Como se genera el code_challenge?
R: code_verifier aleatorio -> SHA-256 -> base64url -> code_challenge, con
   método S256. MSAL lo hace internamente.

Q: ¿ROPC por que no sirve para el API Manager?
R: Porque su issuer es sts.windows.net y el authorizer exige el issuer exacto
   login.microsoftonline.com/<tenant>/v2.0 (el del navegador). Es una
   consistencia con el flujo real.

Q: ¿Donde se guardan los passwords?
R: En el tenant de Azure AD; el usuario nunca entrega la clave a la app ni al
   BFF, solo a Microsoft (SSO). La SPA no conoce passwords.

Q: ¿Que pasa si el token expiro?
R: MSAL lo renueva en silencio (acquireTokenSilent) o redirige al login;
   mientras tanto el API Manager y el backend responden 401.

Q: ¿Por que roles en mayusculas en el backend?
R: Azure manda 'roles' en minusculas (pedidos_admin / pedidos_vendedor); el
   backend los normaliza a ROLE_PEDIDOS_* para @PreAuthorize. No se cambia
   nada en el tenant.

6. COMANDOS RAPIDOS DE EVIDENCIA (si no tienes el script a mano)
--------------------------------------------------------------------------------
$api = "https://pyb1wkfvcg.execute-api.us-east-2.amazonaws.com/prod"
# 401 sin token
Invoke-WebRequest "$api/api/pedidos" -UseBasicParsing
# 200 maria (GET)
Invoke-WebRequest "$api/api/pedidos" -Headers @{Authorization="Bearer $T"} -UseBasicParsing
# 403 maria (PATCH estado -> necesita rol admin)
Invoke-WebRequest "$api/api/pedidos/1/estado" -Method PATCH -Headers @{Authorization="Bearer $T"} -ContentType "application/json" -Body '{"estado":"ENVIADO"}' -UseBasicParsing
# 201 jose (POST), 200 (PATCH), 204 (DELETE) con el token de jose
# Preflight CORS
Invoke-WebRequest "$api/api/pedidos" -Method OPTIONS -Headers @{Origin="http://localhost:4200";"Access-Control-Request-Method"="GET"} -UseBasicParsing
# Backend en EC2 responde (sin pasar por el API Manager)
Invoke-WebRequest "http://pedidos360-alb-dev-2080390497.us-east-2.elb.amazonaws.com/health" -UseBasicParsing
