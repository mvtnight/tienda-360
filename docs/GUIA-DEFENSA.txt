0. RESUMEN DE 30 SEGUNDOS (discurso de apertura)
--------------------------------------------------------------------------------
"Pedidos360 es un sistema de gestion de pedidos. En la etapa 1 implementamos la
seguridad de punta a punta con Azure AD (Entra ID) como proveedor de identidad
(IDaaS):

  SPA Angular + MSAL (login con Authorization Code + PKCE)
  -> BFF Spring Boot :8085 que valida el JWT con las claves publicas de Azure
  -> API Manager en AWS (Amazon API Gateway) que vuelve a validar el JWT
  -> Backend Spring Boot :8090 en EC2 (ALB + Auto Scaling) con autorizacion por
     roles (PEDIDOS_ADMIN / PEDIDOS_VENDEDOR).

El mismo token circula validado tres veces (BFF, API Manager y backend), y las
reglas de rol dan 200, 401 y 403 segun quien haga cada operacion. Tenemos el
flujo funcionando localmente y desplegado en AWS."

--------------------------------------------------------------------------------
1. ARQUITECTURA - FLUJO COMPLETO
--------------------------------------------------------------------------------
1) El usuario abre la SPA (http://localhost:4200) y hace login con Azure AD.
   La SPA usa MSAL v5 con "Authorization Code + PKCE" (no hay secretos, es un
   public client). Redirect URI: http://localhost:4200.
2) MSAL devuelve un access_token cuyo 'aud' es api://6da3f8f4-905c-4c76-abf0-c711d0dd3926
   y cuyo scope es api://6da3f8f4-905c-4c76-abf0-c711d0dd3926/access_as_user.
3) El interceptor HTTP de la SPA agrega el header  Authorization: Bearer <token>.
4) El BFF (:8085) recibe /bff/pedidos y VALIDA el token ANTES de reenviar:
   - descarga las claves publicas JWKS desde la URL de discovery de Azure,
   - valida la firma RS256, el emisor (iss), la audiencia (aud) y exp/nbf.
   Si algo falla devuelve 401 sin llegar al backend. (JwtDecoderConfig.java)
5) Si el token es valido, el BFF reenvia LA MISMA cabecera Authorization hacia
   el API Manager (PEDIDOS_API_URL).
6) El API Manager (API Gateway HTTP API, stack pedidos360-httpapi) tiene un
   JWT authorizer en TODAS las rutas con los MISMOS criterios (issuer del
   tenant y audience api://<client-id>), por lo que un token invalido recibe
   401 y un token valido sin el scope access_as_user recibe 403.
7) El API Manager proxya a un ALB (stack pedidos360-alb) que balancea hacia
   una instancia EC2 (Auto Scaling) donde corre el backend Spring Boot :8090.
   El backend tambien valida el JWT y aplica RBAC por @PreAuthorize.

En el backend hay dos controles de rol importantes:
  - creacion de pedido: PEDIDOS_ADMIN o PEDIDOS_VENDEDOR
  - cambio de estado / cancelacion: solo PEDIDOS_ADMIN
Por eso el mismo endpoint responde distinto segun quien llame: 200, 201, 401, 403.

--------------------------------------------------------------------------------
2. COMPONENTES Y TECNOLOGIAS
--------------------------------------------------------------------------------
- pedidos360-front   : Angular 20 + @azure/msal-angular v5 (standalone).
  - Guards de ruta (auth.guard) redirigen al login si no hay sesion.
  - Interceptor agrega Authorization: Bearer (autorizado para el scope de la API).
  - Dashboard muestra claims del id_token/access_token y roles; boton
    "Copiar access_token (PKCE)" para obtener el token real del navegador.
  - Pedidos lista pedidos y permite crear si el rol lo permite.
- pedidos360-bff      : Spring Boot 3.5 (Java 21 local, JDK 22). Puerto 8085.
  - JwtDecoderConfig: JWKS (RS256) + iss (sts.windows.net/tenant) + aud (client id
    o uri de la API) + exp/nbf.
  - BffController: /bff/pedidos (GET), /bff/pedidos/{id} (GET), POST, PATCH
    /bff/pedidos/{id}/estado y DELETE /bff/pedidos/{id}.
  - BffRestClientService: reenvia el mismo Bearer con RestClient.
- pedidos360-backend : Spring Boot 3.5 con Spring Security OAuth2 Resource Server.
  Puerto 8090. Rutas /api/pedidos..., /health (publico). RBAC con @PreAuthorize.
  - SecurityConfig convierte el claim 'roles' a autoridades ROLE_PEDIDOS_* en
    mayusculas (normaliza el valor que viene en minusculas de Azure).
- infra/              : CloudFormation + deploy.ps1 + user-data (EC2).

5. SEGURIDAD: QUE VALIDA CADA CAPA (para defender)
--------------------------------------------------------------------------
BFF (JwtDecoderConfig):
  - Obtiene JWKS desde https://login.microsoftonline.com/<tenant>/discovery/v2.0/keys
  - Firma RS256; iss = https://sts.windows.net/<tenant>/ ; aud igual al
    client-id o a la App ID URI;
    con exp/nbf obligatorios. Falla -> 401 con JSON de error.
API Manager (AWS):
  - JWT authorizer del API Gateway con IdentitySource = header Authorization.
  - JwtConfiguration.audience = api://<client-id> ; issuer =
    https://sts.windows.net/<tenant>/
  - AuthorizationScopes = access_as_user en todas las rutas (token valido pero
    sin scope -> 403).
  - Todas las rutas del API Gateway estan protegidas, incluida /health.
Backend:
  - OAuth2 Resource Server + @PreAuthorize. Roles normalizados en mayusculas.
    - /health permitAll (para el health check del ALB).
    - PATCH/DELETE solo ADMIN -> maria recibe 403.
  - CORS: http://localhost:4200 y https://d2u1dalj9nm2b1.cloudfront.net.

WEB PUBLICA (CloudFront):

6. POR QUE EL API GATEWAY REQUIERE TOKEN DEL NAVEGADOR (IMPORTANTE)
--------------------------------------------------------------------------
El JWT authorizer de AWS valida el issuer EXACTO que configuramos
(https://sts.windows.net/<tenant>/). La app API no define accessTokenAcceptedVersion,
asi que Microsoft emite tokens v1.0 con ese issuer para TODOS los flujos (navegador
PKCE, ROPC, device code). Por eso el API Manager acepta tanto el token copiado de la
SPA (boton "Copiar access_token") como el ROPC de renovar-tokens.ps1; lo unico que da
401 es un token con issuer de OTRO tenant o firma alterada (caso 12 de la matriz).

11. PREGUNTAS FRECUENTES DEL PROFE (con respuesta)
------------------------------------------------------------------------------
Q: Por que el BFF valida de nuevo el token si ya lo valido la SPA?
R: Porque la SPA es un public client: cualquiera puede llamar al BFF con un
   token de otro. El BFF y el API Manager son la frontera de confianza; validan
   firma/iss/aud/exp antes de reenviar.

Q: Que pasa si el token expiró?
R: El decoder valida exp; MSAL renueva en silencio (acquireTokenSilent) y si no
   puede, redirige al login. El API Manager responde 401 y el backend tambien.

Q: Por que roles en mayusculas?
R: Azure envia el claim 'roles' en minusculas (pedidos_vendedor). El backend los
   normaliza a ROLE_PEDIDOS_VENDEDOR para @PreAuthorize. Es una normalizacion
   determinista, no se cambia nada en el tenant.

Q: El token pasó por BFF y por API Manager; por que validar una tercera vez en
   el backend?
R: Defensa en profundidad. El backend es quien controla los datos, nunca debe
   confiar ciegamente en el header; aplica sus propias reglas RBAC.

Q: Donde queda la contrasena de los usuarios?
R: Son cuentas educativas del tenant del curso; el password sale por ROPC solo
   para pruebas automatizadas (SSO interactivo no lo pide).

Q: Por que no usar el token ROPC en el API Manager?
R: Se PUEDE y se usa (renovar-tokens.ps1). Como la app API no fija version de
   token, todos los tokens (PKCE y ROPC) salen v1.0 con issuer sts.windows.net,
   que es el que valida el authorizer. El token del navegador se usa en la demo
   porque es el flujo real del usuario.
